# Reporting Workflow (Store Lost/Found Reports)

This document describes how a lost/found report is created and validated.

## Flow overview

```
POST /reports  (auth middleware)
  -> StoreReportRequest  (authorize + validate)
  -> LostFoundReportController@store
       DB::transaction {
         1. Create Report (uuid auto-generated by model)
         2. Store uploaded photos in PRIVATE storage -> report_photos
         3. Record item_events entry (action = created)
       }
       GenerateMatches::dispatch(...)->afterCommit()
  -> redirect back with success flash message
```

## Authorization (StoreReportRequest::authorize)

The user must be:

1. Authenticated, and
2. An **active** member (`community_memberships.status = active`) of the
   `community_id` supplied in the request.

Suspended members and non-members receive a `403 Forbidden`.

## Validation rules

| Field         | Rules                                                        |
| ------------- | ----------------------------------------------------------- |
| community_id  | required, integer, exists:communities,id                    |
| category_id   | required, integer, exists:categories,id                     |
| type          | required, in:lost,found                                      |
| title         | required, string, max:120                                    |
| description   | required, string, max:3000                                   |
| color         | nullable, string, max:80                                     |
| brand         | nullable, string, max:100                                    |
| event_at      | required, date, before_or_equal:now                          |
| location_name | required, string, max:255                                    |
| latitude      | nullable, numeric, between:-90,90                           |
| longitude     | nullable, numeric, between:-180,180                         |
| photos        | nullable, array, max:4                                       |
| photos.*      | image, mimes:jpg,jpeg,png,webp, max:5120 (5 MB)             |

## Key design decisions

- **Transactional integrity:** report + photos + audit event are written in a
  single `DB::transaction`, so a failure rolls everything back.
- **Private photo storage:** photos are stored on the `local` disk
  (`storage/app/private`) and recorded with `visibility = private`. They are
  never web-accessible directly.
- **UUID:** the report `uuid` (public identifier) is generated by the model on
  `creating`; it is never accepted from user input.
- **Async matching:** `GenerateMatches` is dispatched with `afterCommit()` so
  the queue worker only runs once the transaction is durably committed. The job
  requires the `Queueable` trait (provides `afterCommit()`).
- **Audit trail:** the initial `item_events` row (`action = created`) records
  who created the report and a small metadata snapshot.
- **Guest redirect:** unauthenticated users are redirected to `/login` via
  `$middleware->redirectGuestsTo(/login)` in `bootstrap/app.php`.

## Testing

`tests/Feature/StoreReportTest.php` covers:

- active member creates a report (photos stored privately, audit event,
  `GenerateMatches` dispatched)
- guest redirected to `/login`
- non-member and suspended member forbidden (403)
- validation errors (missing/invalid fields, future `event_at`)
- too many photos (> 4) rejected
- invalid photo mime type rejected

Run with:

```bash
php artisan test --filter=StoreReportTest
```

> Tests run against PostgreSQL (`findback_testing`) to exercise the real schema
> (jsonb, uuid, enum CHECK constraints). Configure the DB in `phpunit.xml`.
